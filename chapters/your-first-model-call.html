Your first model call

One endpoint carries every model call in this book. This chapter sends the smallest request through Anthropic's Python SDK, changes the conversation and the system prompt to see what each controls, opens the replay switch behind every notebook, and runs the same calls through a command-line client Claude Code generated.

⏱️ ~15 min read
🐍 Notebook included
📊 Chapter 4

A call to Claude is one HTTPS request to the Messages API. The request names a model, caps the length of the reply and carries the conversation as a list of messages, and the response returns the reply as a list of content blocks with the tokens it used. The API keeps no state between calls, so everything the model should know about a conversation travels in each request.

AI
A role marks who wrote a message. user messages come from the person or program asking, assistant messages are the model's replies, and a conversation alternates between them, starting and ending with user. The system prompt sits outside the list and applies to every turn.
🤖
The chapter in one line

The model knows only what the request carries, so the code that builds the request decides what the model can do.

1

A request is three fields and a conversation

The smallest request to client.messages.create names the model, sets max_tokens and sends one user message. The notebook asked Claude Sonnet 5.5 what a context window is.

The reply came back as a message with the role assistant, one text block, the stop reason end_turn and a usage of 20 input tokens and 60 output tokens. Its text read, “A context window is the maximum amount of text (measured in tokens) that a language model can consider at once, including both your input and its own output, so anything beyond that limit is effectively “forgotten.”” The answer lives in the content blocks, so code reads every block of type text, which is what the chapter's answer_text does, and never assumes the answer is the first block. Chapter 5, Reading a response, takes the stop reasons, the usage fields and the errors apart.

The replay helper keeps every request exactly as the SDK sent it, so the recording shows the JSON body on the wire. It is the call's three fields and nothing more:

POST /v1/messages, the body the SDK sent
{
  "max_tokens": 1024,
  "messages": [
    {
      "role": "user",
      "content": "In one sentence, what is a context window?"
    }
  ],
  "model": "claude-sonnet-5-5"
}

The SDK adds the API key and the API version as headers, and the recording keeps neither. A request from another language or from curl sends the same body. Python, Visually's APIs and JSON covers HTTP requests and JSON in Python for readers who want the layer underneath.

2

Roles carry the conversation

Asked “What's my order number?” on its own, the model replied that it had no access to the order information. Sent after two earlier turns, a user message giving order 48213 and an assistant reply, the same question came back as “Your order number is 48213.” The application wrote that assistant turn itself, and the model read it as its own earlier reply. The history a program sends is the only memory the model has.

The same mechanism steers the shape of an answer. The notebook classified three reviews as positive, negative or mixed, once with the instruction alone and once with two worked examples in front of it, each a user turn and the one-word assistant turn the application wanted.

ReviewInstruction aloneWith two examples
The headphones sound great, but the case cracked within a week.Mixed, then a paragraph (63 tokens)mixed (5 tokens)
Arrived two days early and works perfectly.Positive, then a paragraph (68 tokens)positive (4 tokens)

The labels agreed every time. The examples changed only the format, from a bold label and a paragraph of reasons to a single word that code can compare with a string, in 4 or 5 output tokens in place of 58 to 68. Chapter 17, Examples in the prompt, covers how to choose examples and the bias they bring.

3

The system prompt frames every turn

The system field tells the model how to behave across the whole conversation. The notebook sent “My package is late. What should I do?” under three system prompts.

System promptOutput tokensOf them thinkingWhat came back
None64421A numbered guide in six steps
Answer in one sentence.580One sentence
Reply with a JSON object that has the keys action and reply349136JSON that json.loads parsed

One sentence of system prompt cut the reply from 644 output tokens to 58. The JSON instruction produced an object with the keys action and reply that json.loads read without an error, at a cost of 136 thinking tokens. Its action value, request_order_info, was a name the model chose, since the prompt listed no allowed actions, and an instruction alone guarantees neither the format nor the values. Chapter 19, Structured output, adds a schema and validation.

Older Claude models let a request end with a partial assistant turn for the model to continue. As of November 2026, Claude Sonnet 5.5 answers such a request with a 400 error whose message reads “This model does not support assistant message prefill. The conversation must end with a user message.” The chapter's client refuses that shape before sending anything.

4

How the notebooks replay a call

Every notebook in the book builds its client in Setup with book_client.make_client, which returns the SDK's own client with a different transport underneath. The notebook's code is the same SDK call in every mode, and only the place the answer comes from changes.

In replay mode, the default, each request is hashed from its method, path, query and body, and the hash finds the recorded answer. This chapter's recording holds 17 exchanges with Claude Sonnet 5.5, recorded with SDK 2.7.0. The notebook added one question mark to its first request and sent it again, and replay refused with the SDK's NotFoundError:

the message replay gave
book_client: no recorded response for this request (key 23989e7e310591dd) in recordings/your-first-model-call.json. The request differs from the one the notebook recorded. Restore the cell's original code, or set LIVE = True in Setup and use your own key.

A changed request never receives an answer that belongs to a different one, so an edited cell fails with that message. Setting LIVE = True in Setup sends the same requests to the API with your own key, read from Colab's secrets panel or the ANTHROPIC_API_KEY environment variable, and prints live answers that will differ from the recorded ones. Record mode is for the book's own sessions, and the introduction's How the book uses Claude Code explains how the book keeps what it records.

5

Where a first model call goes wrong

  • Reading the first block breaks when a reply carries a thinking block before its text. Join the blocks of type text, as answer_text does.
  • A missing history leaves the model guessing. It couldn't name the order number until the request carried the turn that mentioned it.
  • An unframed question gets a long, general answer. Without a system prompt the late-package question drew 644 output tokens, and one sentence of system prompt brought it to 58.
  • A requested format is followed only as far as the model chooses. The JSON parsed, but its action value was invented, so validate before code acts on it.
  • A final assistant turn is refused by Claude Sonnet 5.5 as of November 2026. End every request with a user message.
6

Build it with Claude Code

The notebook builds its requests, reads its replies and runs its conversations with ask.py, a command-line client that Claude Code wrote against a spec and 23 tests. Here is the spec in full.

spec.md
# ask.py

A command-line client for the Messages API. It sends one question, or a conversation typed line by line, to a Claude model through Anthropic's Python SDK and prints the reply. Apart from the standard library it needs only the SDK, and it imports the SDK only when `main` has to build a client itself, so the functions can be tested with a stand-in client and no key.

## DEFAULT_MODEL and DEFAULT_MAX_TOKENS

`DEFAULT_MODEL` is `"claude-sonnet-5-5"` and `DEFAULT_MAX_TOKENS` is `1024`.

## build_request(prompt, history=None, system=None, model=DEFAULT_MODEL, max_tokens=DEFAULT_MAX_TOKENS)

Return the keyword arguments for `client.messages.create`, as a dict with the keys `model`, `max_tokens` and `messages`, and the key `system` only when `system` is given and not empty. `messages` is a new list holding the messages of `history`, in order, followed by `{"role": "user", "content": prompt}`. Never change the list passed as `history`.

Raise `ValueError` if `prompt` is empty or only whitespace, if `max_tokens` is less than 1, or if `history` is not a valid conversation to add a question to. A valid history is empty, or starts with a `"user"` message, alternates between `"user"` and `"assistant"`, and ends with an `"assistant"` message. A message with any other role is invalid.

## answer_text(message)

Return the text of a response. Join the `text` of every content block whose `type` is `"text"`, in order and with no separator, and skip blocks of every other type, such as `"thinking"`. Return `""` when there are none.

## format_usage(usage)

Return a short description of a response's `usage`, such as `"20 tokens in, 57 out"`. When `usage.output_tokens_details.thinking_tokens` exists and is greater than 0, add how many of the output tokens were thinking, as in `"166 tokens in, 249 out, 103 of them thinking"`.

## chat(client, lines, out, system=None, model=DEFAULT_MODEL, max_tokens=DEFAULT_MAX_TOKENS, show_usage=False, history=None)

Run a conversation. For each string in the iterable `lines`, strip it, skip it if it is empty, and stop at a line that is exactly `/quit`. Send it with `client.messages.create(**build_request(...))`, passing the conversation so far as the history. Write the reply's text to `out`, then the usage line as `[<format_usage>]` when `show_usage` is true, then an empty line, each followed by a newline. Then add the question and the reply to the history, the reply as `{"role": "assistant", "content": message.content}`, so its content blocks go back to the API unchanged.

`history` starts the conversation from earlier messages and is not changed. Return the conversation as a new list of messages.

## main(argv=None, client=None, stdin=None, out=None)

Parse `argv` (the program's arguments when `None`) with `argparse`:

- an optional positional `prompt`
- `--system TEXT`, the system prompt
- `--model NAME`, defaulting to `DEFAULT_MODEL`
- `--max-tokens N`, an integer defaulting to `DEFAULT_MAX_TOKENS`
- `--usage`, which adds the usage line after each reply
- `--chat`, which reads a conversation from standard input, one line per message

`stdin` and `out` default to `sys.stdin` and `sys.stdout`. When `client` is `None`, import `anthropic` and use `anthropic.Anthropic()`, which reads the key from the `ANTHROPIC_API_KEY` environment variable.

With `--chat`, run `chat` over the lines of `stdin`, with `prompt`, when given, sent first. Without it, send one question. The question is `prompt`, or all of `stdin` when no `prompt` is given. If that is empty, write `ask.py: no question given` to `sys.stderr` and return 2. Otherwise write the reply's text to `out` followed by a newline, then the usage line in square brackets when `--usage` is given.

Return 0 when the replies were written. Let errors raised by the client propagate. Chapter 5 handles them.

Running `python3 ask.py ...` calls `main` and exits with its return value.

Its opening sets the one dependency rule that makes the module testable, importing the SDK only inside main, so every function can be exercised with a stand-in client and no key. build_request fixes the exact dictionary sent to the API, down to leaving system out when it is empty, and turns the API's rules about roles into checks that run before anything is sent. answer_text and format_usage settle how a reply is read, skipping thinking blocks and naming thinking tokens only when there are some. chat spells out how a conversation is kept, with the reply's content blocks passed back unchanged, and main lists every option and both exit codes, and leaves API errors to Chapter 5.

These three tests carry most of the spec's weight.

The parametrized test feeds build_request seven requests the API would refuse or that make no sense, an empty prompt, a cap of zero tokens and five broken histories, and expects each to raise ValueError. The chat test checks the second request field by field, so a client that dropped the first reply or passed back only its text would fail. The last test checks that a prompt given with --chat is the first question sent. It checks the order of the requests, and nothing about when standard input is read, which matters below.

import argparse
import sys

DEFAULT_MODEL = "claude-sonnet-5-5"
DEFAULT_MAX_TOKENS = 1024


def build_request(prompt, history=None, system=None, model=DEFAULT_MODEL,
                  max_tokens=DEFAULT_MAX_TOKENS):
    if not isinstance(prompt, str) or not prompt.strip():
        raise ValueError("prompt is empty")
    if max_tokens < 1:
        raise ValueError("max_tokens must be at least 1")
    history = list(history) if history else []
    for i, m in enumerate(history):
        expected = "user" if i % 2 == 0 else "assistant"
        role = m.get("role") if isinstance(m, dict) else None
        if role != expected:
            raise ValueError("invalid history")
    if history and history[-1]["role"] != "assistant":
        raise ValueError("history must end with an assistant message")
    request = {"model": model, "max_tokens": max_tokens,
               "messages": history + [{"role": "user", "content": prompt}]}
    if system:
        request["system"] = system
    return request


def answer_text(message):
    return "".join(b.text for b in message.content if getattr(b, "type", None) == "text")


def format_usage(usage):
    s = f"{usage.input_tokens} tokens in, {usage.output_tokens} out"
    details = getattr(usage, "output_tokens_details", None)
    thinking = getattr(details, "thinking_tokens", None) if details is not None else None
    if thinking and thinking > 0:
        s += f", {thinking} of them thinking"
    return s


def chat(client, lines, out, system=None, model=DEFAULT_MODEL,
         max_tokens=DEFAULT_MAX_TOKENS, show_usage=False, history=None):
    history = list(history) if history else []
    for line in lines:
        line = line.strip()
        if not line:
            continue
        if line == "/quit":
            break
        request = build_request(line, history=history, system=system, model=model,
                                max_tokens=max_tokens)
        message = client.messages.create(**request)
        out.write(answer_text(message) + "\n")
        if show_usage:
            out.write(f"[{format_usage(message.usage)}]\n")
        out.write("\n")
        history = history + [{"role": "user", "content": line},
                             {"role": "assistant", "content": message.content}]
    return history


def main(argv=None, client=None, stdin=None, out=None):
    parser = argparse.ArgumentParser(prog="ask.py")
    parser.add_argument("prompt", nargs="?")
    parser.add_argument("--system")
    parser.add_argument("--model", default=DEFAULT_MODEL)
    parser.add_argument("--max-tokens", type=int, default=DEFAULT_MAX_TOKENS)
    parser.add_argument("--usage", action="store_true")
    parser.add_argument("--chat", action="store_true")
    args = parser.parse_args(argv)
    stdin = sys.stdin if stdin is None else stdin
    out = sys.stdout if out is None else out
    if client is None:
        import anthropic
        client = anthropic.Anthropic()

    if args.chat:
        lines = stdin
        if args.prompt:
            lines = [args.prompt] + list(stdin)
        chat(client, lines, out, system=args.system, model=args.model,
             max_tokens=args.max_tokens, show_usage=args.usage)
        return 0

    question = args.prompt if args.prompt else stdin.read()
    if not question or not question.strip():
        print("ask.py: no question given", file=sys.stderr)
        return 2
    message = client.messages.create(**build_request(
        question, system=args.system, model=args.model, max_tokens=args.max_tokens))
    out.write(answer_text(message) + "\n")
    if args.usage:
        out.write(f"[{format_usage(message.usage)}]\n")
    return 0


if __name__ == "__main__":
    sys.exit(main())

The build took 6 turns and cost 0.0357 dollars on the book's key. The notebook then ran the client against the real recordings, which the tests never did. Review accepted the module, and found one real gap. With a prompt, --chat builds its lines as [args.prompt] + list(stdin), and list reads standard input to the end before the prompt is sent, so at a terminal the first answer waits until the user presses Ctrl-D. The spec never said when input is read, and the test named for the prompt going first checks only the order of the requests. The third practice challenge writes the test that catches it. Review also checked whether main building its client before checking for a question makes a missing key fail first, and found that SDK 2.7.0 creates a client without a key and fails only when a request is sent, so python3 ask.py with no question still prints “ask.py: no question given”. The functions have no docstrings, which the spec didn't ask for. The spec, tests, transcript and generated file are in the repository's builds folder. Copy generated/ask.py to run the client yourself with python3 ask.py --chat --usage "your question", and python3 scripts/claude_build.py your-first-model-call --out my-build repeats the build with your own Claude Code account.

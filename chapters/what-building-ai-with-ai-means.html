What building AI with AI means

The title has two meanings, and the book needs both. A language model can be a component inside the system you build, and an AI assistant can be a collaborator in building it. This chapter puts each to work on eight support tickets, measures what the calls cost, and maps the rest of the book.

⏱️ ~12 min read
🐍 Notebook included
📊 Chapter 1

Traditional code executes deterministically. A language model is a fundamentally different building block. You send text in, get text back, and identical inputs can yield entirely different outputs. Building reliably around that behavior requires traditional engineering discipline adapted for an opaque component. This book teaches that discipline, leveraging the model itself as an assistant throughout the process.

AI
Building AI with AI means two things in this book. A model as a component is a language model your program calls the way it would call any other function or service, and whose output it validates. An assistant as a collaborator is a model that writes code, tests or documents for you, which you accept only after verifying them yourself.
🤖
The chapter in one line

Whether the model runs inside your system or helps you build it, you define what a correct output is, and you verify every output against that definition.

1

What the title means

In the first meaning, the model is a component of the system you build. A support desk might route each incoming ticket through a model that names the team to handle it, and the rest of the desk's software acts on that output. In the second meaning, the model is a collaborator in the engineering process. You specify a function, an assistant writes it, and tests you wrote decide whether it ships. Most chapters cover the first meaning. From Part 2 on, every chapter also applies the second, with Claude Code generating the code the chapter needs from a spec and tests, and Chapter 137, How this book is built, shows the workflow behind this book.

The models behind both are the large language models the first book introduces in NLP and large language models. This book treats them as building blocks, so it starts from their interface, the text you send and the text that comes back.

2

A model behind a function call

The chapter's notebook defines triage, a function that takes a ticket and returns one of four categories: billing, login, shipping or other. Inside, it sends the ticket to Claude Sonnet 5.5 with a short instruction, the system prompt, that lists the categories and asks for exactly one word. Its last line is a guard. Any reply that isn't one of the four comes back as unrecognized, so a stray answer can't pass for a category further on. The request itself is an HTTP call to Anthropic's API, the kind Python, Visually covers in APIs and JSON.

The triage routine evaluates ticket payloads and invokes a large language model (LLM) to perform categorical classification. The sample output below illustrates the input tickets alongside the model's inferred category assignments.

Every reply was one of the four categories, so the guard never fired. Six tickets have one plain answer. The other two are judgment calls. The crushed box went to shipping, though it could also be read as a damaged-goods complaint, and the invoice ticket went to login, though what the customer wants is a billing document. A program that routes tickets on these labels inherits both judgments, which is why Part 3 measures a function like this one against a test set before anyone relies on it.

3

An assistant that writes code you verify

The second half of the notebook asks the same model for code. It requests normalize_label, a function that turns a messy one-word reply such as " Billing.\n" into a clean category. Before the reply was read, the book wrote six cases the function has to pass, among them a capitalized word, trailing punctuation, a word outside the list and an empty string. This is the function that came back.

written by the model
import string

VALID_LABELS = {"billing", "login", "shipping", "other"}


def normalize_label(raw: str) -> str:
    if not isinstance(raw, str):
        return "other"

    cleaned = raw.strip().lower()
    cleaned = cleaned.strip(string.punctuation + string.whitespace)

    return cleaned if cleaned in VALID_LABELS else "other"

All six cases pass, so the function is accepted. It also handles something the request never asked for, returning other when the reply isn't a string at all. The notebook runs the code with exec, which would run whatever the model had written, so the code is reviewed before it runs. The cases are the contract, and the practice of writing them is covered in Python, Visually's Testing and Packaging.

The solutions notebook sent the identical request again and got back a slightly different function, with fewer blank lines and with whitespace and punctuation listed in the other order. It did the same job and passed three more cases. Two identical calls returned two versions of the code, and the same cases would have caught one that behaved differently.

4

What each call costs

Every response reports its input and output token counts, and the API bills on those counts. The notebook's nine calls read 665 tokens and wrote 337, about half a cent at Claude Sonnet 5.5's prices as of November 2026, which were 2 dollars per million input tokens and 10 dollars per million output tokens.

Five tickets were answered in 3 to 5 output tokens. The gift cards, the crushed box and the invoice took 93, 48 and 34, and most of each was thinking. On those three the model reasoned before it answered, and the reasoning is billed as output although its text isn't returned. It arrives as a thinking block with nothing in it, which is why the notebook reads only the text blocks of a reply. The tickets that needed a judgment call cost the most. Chapter 3, Tokens, context and cost, takes the counting further.

How the book is organized

The parts follow the order in which a production system comes together. Part 1 covers the request and response cycle, and Part 2 sets up Claude Code, which generates the code in every chapter after it. Part 3 treats a prompt as code. Part 4 comes early on purpose, because every later part needs evals to measure what it builds, and Part 5 grounds the model in documents through retrieval-augmented generation. Parts 6 to 15 design agent systems: the engineering principles behind them, tools and agents, memory and state, the harness that lets a model act, skills, MCP servers and clients, multi-agent systems and their orchestration, agent-to-agent communication, the open-source frameworks, and the clients users reach agents from, such as Claude, Gemini, Slack and Microsoft Teams. Where a chapter needs statistics, such as a confidence interval around a pass rate, it links to the first book. Where it needs Python or a library, it links to a guide in Python, Visually, starting with Python from the Start.

6

Where building AI with AI goes wrong

A model's reply is text, and nothing forces it into your categories. The notebook passes four sample replies through the strict check in triage and through the model's normalize_label.

ReplyStrict checknormalize_label
'billing'billingbilling
'Billing.'unrecognizedbilling
'refund'unrecognizedother
'I think this is a login problem.'unrecognizedother

The strict check stops Billing. because of a capital and a period, so a human or a retry has to handle a case that trivial normalization would have resolved. The normalizer accepts it, and also files the word refund and a whole sentence under other without saying the model failed to answer. Each design has its own failure mode, and a system built on a model has to choose the one it can tolerate and measure how often it occurs.

The chapter surfaced other failure modes as well. Two labels were judgment calls, and only a test set can say how often such calls go the right way. The same request for code returned two versions, so a result seen once can't be assumed next time. The hardest tickets cost the most, through thinking that a reply doesn't show. And model-written code executes whatever it contains, so it is reviewed and tested before it runs. None of this showed as an error in the eight tickets, where every reply was clean, and one good run says little about the next thousand.

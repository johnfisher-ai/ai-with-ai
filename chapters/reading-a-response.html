Reading a response

A reply that looks fine can be cut off, and a call that fails can fail for a reason no retry will fix. This chapter reads why each reply stopped, what it consumed and how each failure is typed, then retries through a busy API with a module Claude Code generated from a spec and tests.

⏱️ ~15 min read
🐍 Notebook included
📊 Chapter 5

Every response from the Messages API carries more than its text. stop_reason says whether the reply finished or was cut off, usage accounts for every token, and a failed call raises an exception typed by its HTTP status. Code that reads only the text treats a truncated reply as a complete one and retries errors that will fail the same way every time.

AI
A retryable error is one that a later attempt of the same request may not hit: a rate limit, an overloaded server, a timeout or a dropped connection. A request error, such as an unknown model or an empty message, fails the same way on every attempt.

The chapter in one line

Read stop_reason before the text, and retry only what time can fix, waiting as long as the API asks.

Anthropic's error reference lists the rest of the statuses as of November 2026, among them 401 for a bad key, 403 for a key without permission, 413 for a request that is too large, 429 for a rate limit, 500 for an internal error and 529 when the API is overloaded. An error response also carries a request ID, which the book's recordings drop before anything is saved.

4

Retries that wait the right amount

As of November 2026 the API limits each organization by requests, input tokens and output tokens per minute, replenished continuously like a bucket refilling, and a request over a limit gets a 429. Its retry-after header, when present, gives the seconds to wait, and earlier retries fail. A 529 means the API is overloaded, which Anthropic's error reference ties to high traffic across all users. Neither can be recorded on demand, so the notebook built the two errors the way the SDK does, raised them in front of a real request and let the chapter's call_with_retries work through them.

The 529 carried no header, so the wait came from exponential backoff with full jitter, a random fraction of a ceiling that doubles with each failure, here 0.62 seconds. The 429 asked for 2 seconds and got exactly that. The request for an unknown model was raised after one attempt and no wait. Not every 429 is worth retrying. A 429 that reports the organization's spend cap carries the error code enforced_spend_limit_reached, and Anthropic's documentation says retries fail until access resumes.

The SDK retries on its own, twice by default as of SDK 2.7.0, on 408, 409, 429, every 5xx status and dropped connections, honoring retry-after. Its own loop is the right choice for most code. A wrapper of your own earns its keep when the program needs to log each retry, cap the total wait or share a budget across calls, and then the SDK's retries should be turned off, because a default client inside a four-attempt wrapper can send up to 12 requests for one call.

5

Where reading a response goes wrong

  • An unchecked stop reason passes a truncated reply off as finished. The 40-token reply came back with no text at all, so check for max_tokens before using the text.
  • A tight cap forgets thinking. Thinking tokens come out of max_tokens too, and here they used all of it.
  • Retrying request errors spends time and quota on a failure that can't change. A 400 or 404 is raised at once by is_retryable.
  • Fixed retry delays send clients back in step. Jitter spreads them out, and retry-after, when the API sends it, overrides both.
  • Stacked retry loops multiply the requests. Keep one in charge, the SDK's or your own.
6

Build it with Claude Code

The notebook's retrying comes from retry.py. The book wrote its spec from Anthropic's published error and rate-limit pages, wrote 29 tests, and had Claude Code write the module.

spec.md
# retry.py

Retries for calls to the Messages API. It decides which errors are worth another attempt, how long to wait before it, and runs a call until it succeeds, fails for a reason no retry can fix, or runs out of attempts. It uses the standard library and Anthropic's Python SDK, whose exception classes it reads.

## is_retryable(error)

Return `True` for an error that a later attempt of the same request may not hit, and `False` for every other error.

- `anthropic.APIConnectionError`, which includes `anthropic.APITimeoutError`, is retryable.
- `anthropic.APIStatusError` is retryable when its `status_code` is 408, 409 or 429, or 500 or more, which covers 529, the status Anthropic's API returns when it is overloaded.
- One 429 is not retryable. When the organization has reached its spend cap, the error's `body` is a dict whose `error.details.error_code` is `"enforced_spend_limit_reached"`, and retries fail until access resumes.
- Any other exception, including a status error such as 400, 401, 403 or 404, is not retryable.

## retry_after(error)

Return how many seconds the API asked the client to wait, as a float, from the `retry-after` header of a status error's `response`. Return `None` when the error has no response, the header is missing, or its value is not a number of seconds that is 0 or more.

## backoff_delay(attempt, base=1.0, cap=30.0, rng=random.random)

Return the delay before the next attempt with exponential backoff and full jitter. `attempt` counts the attempts that have failed so far, starting from 0 for the first. The delay is `rng()` multiplied by the smaller of `cap` and `base * 2 ** attempt`, so it lies between 0 and that ceiling. `rng` returns a float in [0, 1), and tests pass their own.

## call_with_retries(fn, max_attempts=4, base=1.0, cap=30.0, sleep=time.sleep, rng=random.random, on_retry=None)

Call `fn()` with no arguments and return what it returns. If it raises a retryable error and attempts remain, wait and call it again. `max_attempts` counts every call, the first included, and must be at least 1, or `ValueError` is raised before `fn` is called.

The wait is `retry_after(error)` when that is not `None`, because the API knows when capacity returns, and `backoff_delay(attempt, base, cap, rng)` otherwise. Before each wait, call `on_retry(number, error, delay)` when it is given, where `number` is the attempt that just failed, counting from 1. Then call `sleep(delay)`.

A non-retryable error is raised at once, unchanged. When the last attempt fails, raise its error unchanged, so the caller handles the same exception the SDK raised.

## create_with_retries(client, request, **options)

Send `client.messages.create(**request)` through `call_with_retries`, passing `options` on to it, and return the response. The SDK's client retries on its own, twice by default, and retries stacked on retries multiply the attempts. So send the request through `client.with_options(max_retries=0)`, which leaves the retrying to this module.

is_retryable carries the policy, and its bullets copy the documented split between conditions that clear and requests that are wrong, with the spend cap called out as the one 429 that doesn't clear. retry_after defines exactly which header values count, so a malformed header falls back to backoff instead of crashing the retry loop. backoff_delay gives the formula and takes the random source as an argument, which is what lets a test pin the delays. call_with_retries settles the details a loop gets wrong, what max_attempts counts, which wait wins, when the callback runs and that the caller sees the SDK's own exception. create_with_retries says why the SDK's retries are switched off.

Three of the tests check the decisions most worth getting right.

tests/test_retry.py, three of its tests
def test_a_spend_cap_429_is_not_retryable():
    error = api_error(429, error={"type": "rate_limit_error", "message": "Fixture spend cap.",
                                  "details": {"error_code": "enforced_spend_limit_reached"}})
    assert is_retryable(error) is False


def test_rate_limits_wait_as_long_as_retry_after_says():
    fn, slept = Flaky(api_error(429, {"retry-after": "3"}), api_error(429, {"retry-after": "3"})), []
    assert call_with_retries(fn, sleep=slept.append) == "done"
    assert fn.calls == 3 and slept == [3.0, 3.0]


def test_create_with_retries_turns_off_the_sdks_own_retries():
    client, slept = FakeClient(), []
    request = {"model": "claude-sonnet-5-5", "max_tokens": 64, "messages": [{"role": "user", "content": "Hi"}]}
    assert create_with_retries(client, request, sleep=slept.append, rng=lambda: 1.0) == "a message"
    assert {"max_retries": 0} in client.options and client.requests == [request, request]
    assert slept == [1.0]

The first builds a 429 with the spend-cap error code and expects no retry. The second fails twice with retry-after: 3 and checks that the module slept exactly 3 seconds each time, through a list standing in for time.sleep, so the test takes no time at all. The third hands create_with_retries a client that records its options, and checks that max_retries=0 was asked for and the request was sent twice. Every error in the tests is built from the SDK's real exception classes, so the module is tested against the types it will meet.

import math
import random
import time

import anthropic


def _spend_cap_reached(error):
    body = getattr(error, "body", None)
    if not isinstance(body, dict):
        return False
    inner = body.get("error")
    if not isinstance(inner, dict):
        return False
    details = inner.get("details")
    return isinstance(details, dict) and details.get("error_code") == "enforced_spend_limit_reached"


def is_retryable(error):
    if isinstance(error, anthropic.APIConnectionError):
        return True
    if isinstance(error, anthropic.APIStatusError):
        status = error.status_code
        if status == 429 and _spend_cap_reached(error):
            return False
        return status in (408, 409, 429) or status >= 500
    return False


def retry_after(error):
    response = getattr(error, "response", None)
    if response is None:
        return None
    value = response.headers.get("retry-after")
    if value is None:
        return None
    try:
        seconds = float(value)
    except (TypeError, ValueError):
        return None
    if not math.isfinite(seconds) or seconds < 0:
        return None
    return seconds


def backoff_delay(attempt, base=1.0, cap=30.0, rng=random.random):
    return rng() * min(cap, base * 2 ** attempt)


def call_with_retries(fn, max_attempts=4, base=1.0, cap=30.0, sleep=time.sleep,
                      rng=random.random, on_retry=None):
    if max_attempts < 1:
        raise ValueError("max_attempts must be at least 1")
    attempt = 0
    while True:
        try:
            return fn()
        except Exception as error:
            if not is_retryable(error) or attempt + 1 >= max_attempts:
                raise
            delay = retry_after(error)
            if delay is None:
                delay = backoff_delay(attempt, base, cap, rng)
            if on_retry is not None:
                on_retry(attempt + 1, error, delay)
            sleep(delay)
            attempt += 1


def create_with_retries(client, request, **options):
    c = client.with_options(max_retries=0)
    return call_with_retries(lambda: c.messages.create(**request), **options)

The build took 6 turns and cost 0.0323 dollars on the book's key. Review accepted the module unchanged. The extra check is a real fix. float("nan") parses and is not less than 0, so it passes the spec's check for a negative wait, and an infinite wait would hang the program. Review also found a gap the spec left. call_with_retries waits as long as retry-after says, however long that is, and the third practice challenge adds a ceiling without changing the module, through its on_retry callback. The functions have no docstrings, which the spec didn't ask for.
